# How member content stays accountable

Signed-in family members can write things on the site: posts on their own page, comments on person records and posts, emoji reactions, and photos attached to posts. They can also choose which of those events reach their phone as push notifications. All of this runs through one small API, `hfy-api`, which stores its records in one DynamoDB table (photos go to S3). The API has two front doors. The site's islands call its HTTP routes under `/api/*`. An AI assistant that a member connects calls the MCP tools at `/mcp`, which the same Lambda serves and which run the same route handlers.

This page explains the rules that API enforces and why each one exists. Most of them follow from two program decisions: who may change what (BRD decision Q-4), and that every change leaves a record (BRD decision D-15). Routes, payloads and error codes are in the [API reference](../reference/api.md). The tools, their policy and the groups that unlock them are in the [MCP server reference](../reference/mcp-server.md). The key layout of the table is in the [architecture reference](../reference/architecture.md).

## Members only, reads included

Every route the API serves under `/api/*` requires a session, and that includes reads. Listing posts, reading a comment thread and fetching the push public key all return 401 without a valid session cookie, exactly as a write does. The capability document generated from the route registry says so (`reads_require_session: true`), and [`api/test/api.test.js`](../../api/test/api.test.js) checks reads and writes alike.

Reads are not exempt because the content is about the family and written for the family. A comment on a person record often discusses a living relative, and a post may mention addresses, dates or health news. There is no audience for this material outside the family, so there is no reason to give it a public path. A single rule with no exceptions is also easier to check than a list of routes that happen to be public. The person records get the same rule from the private data gate, which checks the same session at the edge and was attached at the 2026-10-12 cutover ([family data privacy](family-data-privacy.md#gating-the-json)). Post photos are not served by the API at all. CloudFront serves them from the bucket, and the gate covers their path too, so a gated photo needs the same session as a post (see [Photos are members-only](#photos-are-members-only)).

The session is the `io_id` cookie that the auth edge issues at sign-in. The API verifies it against the public keys the edge publishes. It never holds the signing key, so a compromise of the API cannot mint sessions. The token's subject is the member's Gramps ID, which makes a member's identity and their place in the family tree the same identifier. [The identity model](identity-model.md) explains that choice. Before any of this, the Lambda rejects a request that did not come through CloudFront ([edge and origin design](edge-and-origin-design.md)).

The MCP door keeps the same rule with a different credential. Every call to `/mcp*` must carry a bearer access token that the auth edge issued for the resource `https://<site>/mcp`. The mount in [`api/src/mcp.js`](../../api/src/mcp.js) verifies it against the same published keys and checks its issuer, its client and its audience. The API's cookie check is never consulted there. A token shows that the caller is a member, because the edge issues one only to a member on the allowlist. It does not by itself unlock any tool. Tools come from the groups config described below, and a member in no group sees an empty tool list. The only content the Lambda serves without a credential is the protected-resource metadata under `/.well-known/oauth-protected-resource`, which tells an MCP client where to sign in and holds no family content.

## Authors edit, admins only remove (Q-4)

The moderation model is deliberately small. The table below summarises it. The authoritative tables, with the status code for each denial, are under [Permissions](../reference/api.md#permissions) in the API reference. The MCP tools apply the same rules through the same handlers, but offer fewer actions (see [Agents draft and propose](#agents-draft-and-propose)).

| Action on a post or comment | Its author | An admin (on someone else's) | Any other member |
| --- | --- | --- | --- |
| Edit the text | Yes | No | No |
| Publish, withdraw or return a post to draft | Yes | No | No |
| Delete | Yes | Yes | No |
| See a draft or withdrawn post | Yes | Yes | No |
| React to a comment | No (own items) | Yes | Yes |

On the site, admins are the members whose Gramps IDs appear in `config/admins.json` in the private config bucket ([private data and secrets](../reference/private-data-and-secrets.md)). The API reads that list, caches it for 60 seconds and fails closed. If the list cannot be read, nobody is an admin until it can be, and the API retries after five seconds. The file may also be absent, and that is a supported state: the site then has no moderators, and the API keeps failing closed, logging `admin list unavailable (failing closed)` each time it retries. Neither case grants moderation to the wrong person. Because admin status comes from the list and not from the session token, adding or removing an admin takes effect within a minute without anyone signing in again ([manage family access](../how-to/manage-family-access.md)).

For a call through the MCP tools, admin means something else: membership of the `hfy-admin` group in `config/groups.json`, which names its members by subject (Gramps ID) only. The mount builds the same `{id, label, admin}` actor that the site's session check builds, with `admin` set from that group. The handlers therefore apply Q-4 without knowing which door a request came through. The groups file is cached and fails closed in the same way as the admin list, and any groups the access token itself carries are ignored. Neither list implies the other. A moderator on the site is not an MCP admin unless `config/groups.json` says so, and [the identity model](identity-model.md#admins-are-a-separate-list) explains why the lists are kept apart.

### The server computes `can`

Every post and comment the API returns carries a `can` object (`edit`, `delete`, and `publish` or `react`) computed for the member who asked. The islands never offer more than that object allows. The comments kit shows a comment's edit and delete controls, and the admin moderation menu, only when that comment's `can` allows them. The posts islands draw a post's delete button only when `can.delete` is true, and they always narrow `can.publish` to false, because the site has no publish control ([`islands/src/lib/content-source.js`](../../islands/src/lib/content-source.js)). They may hide a control the server allows, but they never work out authority themselves.

There are two reasons for this. First, the client cannot know who is an admin, because the list is private and changes without a redeploy. Second, the same policy function that fills in `can` also guards the write in [`api/src/content.js`](../../api/src/content.js) and [`api/src/comments.js`](../../api/src/comments.js). A button that appears is therefore a button that will work, and a forged request for an action without a button gets 403 (or 404 for a post the caller may not see).

### Why removal is allowed but alteration is not

An admin needs some way to deal with a post or comment that should not be on the family site. Deleting it is enough for that job. Editing it is not needed, and editing would be harmful.

A deleted item is gone, and everyone can see that it is gone. An edited item still carries its author's name over words its author did not write. On a site where relatives speak about each other, putting text in someone's mouth does more damage than taking it down. Removal also loses nothing: the audit record of the delete keeps the full text in its `before` snapshot (see the next section). An admin who deletes someone else's comment can also give a reason, which is stored on that audit record.

The same reasoning keeps visibility author-only. Publishing or withdrawing a post is a decision about the author's own words, so an admin's only action on another member's post is to delete it. The comments kit has an `adminCanEdit` option for hosts that want wider powers. The harrisonfamily API does not set it.

### A discussion is as visible as its post

The comments under a post are part of what the author published. If withdrawing the post left its comments readable, withdrawal would hide the author's words but not the replies that quote and discuss them. So the API treats a `post:<ulid>` thread exactly as it treats the post (HFY-R58): a member who cannot see the post cannot list the thread, add to it, edit in it or react in it, and gets the same `404` as for the post itself. Comments on person records have no such parent and are unaffected.

One action is deliberately left open. An author can always delete their own comment, and an admin can always remove one, even under a withdrawn post. Withdrawal must never trap words that their author wants gone.

Deleting a post takes its discussion with it. A comment thread with no post above it has no context and no owner who can hide it, so the API removes every comment and reaction in the thread after the post's delete commits. Each removed comment gets its own audit record, attributed to the member who deleted the post, with the reason `post deleted`. The cleanup runs after the post delete and cannot undo it. If it fails part way, the post stays deleted and the remaining comments stay in the table, unreachable through any route.

## Every change carries its own audit record (D-15)

D-15 is a standing invariant. Family data may be created or edited only by a signed-in member, and only with an audit trail that records who made the change, when, and the state before and after. It applies now to posts and comments, and it will bind genealogy editing when that is added.

The API meets it by writing the data change and its audit item in one DynamoDB `TransactWriteItems` call ([`api/src/txn.js`](../../api/src/txn.js)). Creating, editing, deleting or changing the visibility of a post, and creating, editing or deleting a comment, each produce one transaction. That transaction holds the post or comment items and one `AUDIT#` item with `{op, id, principal, at, before, after}`. Either all of it is written or none of it is. A change without an audit record cannot exist, and neither can an audit record of a change that never happened. That guarantee rests on DynamoDB's `TransactWriteItems`. The tests in [`api/test/hardening.test.js`](../../api/test/hardening.test.js) force cancelled transactions in the in-memory DynamoDB fake, racing edits against withdrawals, deletes and other edits, and check that the losing write leaves neither data nor an audit item behind.

The main item's write is also conditional. A create requires that the id is new. An edit, visibility change or delete requires that the record still holds exactly the version the API read: the same `updated_at` for a post, the same `edited_at` for a comment (HFY-R58). If two members, or two tabs, change the same record at once, the second write is refused with `409 conflict` instead of silently overwriting the first. That matters for D-15 as much as for the data. An unconditioned write would record a `before` that was no longer true by the time it landed, so the trail would show one change and lose the other. With the condition, every audit `before` is exactly the version the change replaced. An edit that races a delete fails too, rather than bringing the record back without its history.

Audit items are keyed by the record they describe and ordered by time, and they also share one index partition. The history of one post or comment is a single query, and so is the whole site's change log. Audit items have no expiry. The table keeps point-in-time recovery on, and the stack retains the table if the stack is deleted.

The handler also accepts an in-process audit callback. The contract suites use it to check that each operation emits exactly one entry. In production the durable trail is the `AUDIT#` item, not the callback. A comment edit that leaves the text unchanged, or a visibility change to the visibility a post already has, writes nothing and is not audited.

### Why reactions are not audited

A reaction is written and removed with a plain put or delete, outside any transaction and without an audit item. That is deliberate.

D-15 protects content that members author. A reaction contains no text. It is one emoji from one member on one comment, and the stored item already names who made it. Tapping the same emoji again removes it, so the reacting member can undo it at any time, and nobody else can change it. If each toggle were audited, the audit log would fill with taps and the content changes would be harder to find. When a comment is deleted, its reactions are deleted in the same transaction as the comment and its audit item. The audit record keeps the comment but not the reactions.

## Labels that never publish an address

Every post and comment names its author with a label, `author.label`, and every member who can see the item sees it. A level-1 push notification uses the same label to name the actor. HFY-R68 settled that this label is never an email address.

The obvious source would be the sign-in itself, and it is the wrong one. The session's `name` comes from the member's allowlist entry. Most entries in `config/userGrampsID.json` are plain strings that map an email to a Gramps ID and give no name, and for those the auth kit falls back to the member's email. Taking the session's label as given would print most members' addresses under everything they write, where any relative could copy them.

So [`api/src/labels.js`](../../api/src/labels.js) chooses the label in a fixed order:

1. **The `name` from the session or access token,** but only when it is usable: not empty, not just the Gramps ID, at most 200 characters, with no control characters and no `@` anywhere in it.
2. **Otherwise, the person's `displayName`** from their own record on the site, `person/<gramps-id>.json`. That is the name the family tree already gives them, so using it tells members nothing they could not already see. The API's role may read `person/*` for this and nothing else among the data prefixes.
3. **Otherwise, the Gramps ID itself.** An opaque ID under a comment is awkward, but it leaks nothing. If even the Gramps ID contained `@`, the label would be `family member`.

The `email` claim of an access token is never a candidate. Rejecting anything that contains `@` also catches an address embedded in a longer string.

The order is the same on both doors. The site's session check ([`api/src/auth.js`](../../api/src/auth.js)) and the MCP mount use one resolver, so a member has one label whether they wrote in the browser or through an assistant. The record lookup costs an S3 read, so each Lambda container caches a label it found for an hour. It caches a missing record, or one with no usable name, for a minute, and a failed read for five seconds, so a brief S3 error does not stamp the Gramps ID onto a run of new comments. A label problem never rejects a valid session or fails a write. The resolver does not throw, and it falls back to the Gramps ID.

The label is copied when the item is written. It is stored on the post's main item and its index items, on the comment, and inside the `before` and `after` snapshots of the D-15 audit entries. An edit keeps the stored author, and nothing in the repository rewrites a label afterwards. A later change to a person's `displayName` does not relabel their old content. Content written before HFY-R68 keeps the label it was stored with, which may be an email address, and no edit changes it. That fits D-15. Rewriting stored labels would be a change to member content that no member made, outside any audited transaction.

## A name leads to the person, and a photo's words are shown

Two of io's design rulings shape how member content is read. The facts are in the [front-end reference](../reference/front-end.md#person-names-and-photo-captions).

**Every name is a link to its person (ruling P2-R46).** The site exists to connect people to their family. A name under a post, beside a comment or under a tagged photo is the natural way in to that person's page, so it is always a link, styled to look like the name and not like a link: the same colour and weight, with no underline. The author's stored principal already carries the Gramps ID, so the link needs no lookup and no new data. A principal without a Gramps person ID has no page to open, and its name stays plain text rather than linking somewhere wrong. One rule in the islands decides this for every surface, so the posts, the comments and the photo tags cannot drift apart. Under a tagged photo the name used to be the button that showed the tag's data; ruling P2-R53 made the name a link there too and moved the data behind a small icon button beside it, so a tap on a phone can still reach both.

**A photo's text is its caption (ruling P2-R47).** When members type something about a photo, they write it for their relatives to read, not as hidden text for screen readers. The composer's field therefore asks for "a caption", and every post shows the text under its photo. Screen-reader users still need to know that a photo is there and whose it is, so the image's own alt says so ("a photo from <name>"). It does not repeat the caption, which the figure already announces.

## Agents draft and propose

A member can connect an AI assistant to the site through the MCP tools ([agents as members](identity-model.md#agents-as-members)). The assistant acts with the member's access token, so it can never do more than the member could. The tool surface is built so that it does less.

- **Tool calls go through the route handlers.** Each tool is generated from a route in [`api/src/routes.js`](../../api/src/routes.js) and runs that route's own handler, through `invoke` in [`api/src/handler.js`](../../api/src/handler.js), as the member's actor. Validation, the Q-4 checks, the D-15 transaction with its audit item, and the notifications after commit therefore apply to a tool call exactly as they do to a click in the site. No rule has a second copy that could drift from the first. The visibility rules for drafts, withdrawn posts and their threads apply unchanged, with admin decided by `hfy-admin` as described above.
- **Fewer actions than the site.** There are seven tools: list, get and create posts, list and create comments, and delete posts and comments. No tool edits, publishes, withdraws, reacts, uploads or changes notification settings. An assistant can add words to the site, but it cannot change words already there.
- **A new post is always a draft.** `hfy_posts_create` has no visibility argument and always sets `visibility: "draft"`, whatever the caller sends. A draft is visible only to its author and admins, and the new-post notification goes out only when a post is published. No tool publishes, and an assistant's access token cannot call the API's own routes, which accept only the `io_id` session cookie. Nothing an assistant drafts reaches the family unless the member publishes it with their own session, so publishing stays a human act. The site does not offer that step yet. The posts islands publish a new post in one gesture, list only published posts and have no publish control ([front-end reference](../reference/front-end.md)), so today a draft can be published only through the API's visibility route, `POST /api/posts/:id/visibility`. A comment has no draft state. `hfy_comments_create` posts at once, under the member's label, and notifies like any other comment.
- **Writes can be proposed first.** Every write tool accepts `mode: "dry_run"`. The call then returns the fully resolved call (the tool, its arguments, the caller and the policy decision) and writes nothing, so an assistant can show its member what it intends before it acts. The policy table in [`api/src/policy.js`](../../api/src/policy.js) also gives both create actions and every delete `agentMode: "dry_run"`, which means that a caller the MCP kit identifies as an agent, rather than as the member, may only dry-run them. The kit's edge, at the version in use, marks every caller as a person rather than an agent, so that rule is published but never applied, and a call without `mode` executes ([MCP server: Dry runs](../reference/mcp-server.md#dry-runs)).
- **Deletes need an admin who was just verified.** The delete tools are shown only to `hfy-admin`. To anyone else they do not exist, and calling one gets the same error as an unknown tool. So a member outside `hfy-admin` cannot delete even their own post or comment over MCP; that stays in the site. An admin also needs a fresh step-up: the access token must show a sign-in within the last 300 seconds in which the authenticator verified the user (`amr` contains `mfa`). Until then the delete tools are listed but disabled, with `step_up_required`. Deletion is the only destructive tool, and a post's delete takes its whole discussion with it. An assistant can keep refreshing its access for weeks, so the step-up makes sure a person was present and verified moments before anything is removed ([step-up for destructive agent actions](identity-model.md#step-up-for-destructive-agent-actions)).
- **The call log is separate from the content audit.** Each call to a listed tool, whether it ran, was refused or was a dry run, writes one `mcp.audit` line to the API's CloudWatch logs. The line names the tool, the mode, the outcome, how and when the member signed in, and the caller's subject and groups. It carries no arguments, results or label, and it is not written to DynamoDB. A tool call that changes content still writes its own `AUDIT#` item through the route handler, so the D-15 trail is the same whichever door a change came through. The log answers a different question: what an assistant tried, including refused calls and dry runs that changed nothing. Those are not content changes, and keeping them out of the table follows the same reasoning that keeps reactions out of the audit trail.

## CSRF defence without tokens

The session cookie is `HttpOnly`, `Secure` and `SameSite=Lax`. Lax means that, for a request started by another site, the browser attaches the cookie only to a top-level GET navigation. It leaves the cookie off cross-site form posts and scripted requests, and every GET route on the API is a read. `@io-kit/auth` sets Lax rather than Strict because WebKit withholds Strict cookies after a cross-site redirect chain. harrisonfamily has its own reason to keep Lax. Under Strict, a member who arrives by a cross-site top-level navigation, such as a link in an email or an MCP client's authorize step, would look signed out on that first request.

Lax alone leaves a gap. The cookie is host-only (the edge strips the kit's `Domain` attribute in [`auth/src/edge.js`](../../auth/src/edge.js)), but SameSite is decided by site, not by origin. A page on any sibling subdomain of the family domain is therefore same-site, and the browser attaches the cookie to the requests it makes to the site. The second rule closes that gap. The API answers any POST, PUT or PATCH whose `Content-Type` is not `application/json` with 415, before it reads the body ([`api/src/handler.js`](../../api/src/handler.js)). An HTML form can only send form encodings or plain text. A script on another origin that sets a JSON content type, or uses DELETE, triggers a CORS preflight, and the API grants none.

Together the two rules do the job of a CSRF token without one. The islands' API client already sends a JSON content type on every request with a body, so the defence costs nothing on the client. A token scheme would need server-side state or a double-submit cookie, and every island request would have to carry it.

The MCP door needs neither rule. It reads no cookie, only a bearer token in the `Authorization` header, and a browser never attaches a bearer token to a request on its own.

## One table for the app and the auth edge

Decision D-10 gave the site one small backend on a single DynamoDB table. The table `hfy-app` holds posts, comments, reactions, audit items, push subscriptions and notification preferences. It also holds the auth edge's records: refresh sessions, identity links, passkey credentials (`PASSKEY#`) and the single-use WebAuthn challenges (`PASSKEYCHAL#`), the forgot-password counters (`RATE#`), and the MCP authorization records. Each kind has its own key prefix. The table has one secondary index (`GSI1`) and one TTL attribute, and any kind that needs an index or an expiry uses these.

At family scale a second table would add operational surface and no capacity. One table means one resource to encrypt, recover, retain and pay for on demand. An idle on-demand table costs only its storage ([cost estimate](../reference/cost-estimate.md)).

### Why index items carry a full copy of the post

A post is stored as up to three items: the main item, an author index item and, if the post has a subject, a subject index item. Each of the three carries the whole post, and the index projects all attributes. Listing the homepage timeline, one member's posts or the posts about one person is therefore a single query on the index, and the results are the posts themselves. No second round of reads is needed to fetch post bodies.

The price is that every write rewrites each copy. The copies cannot drift apart, because they are written in the same transaction as the audit item. The size limits follow from the copies. The audit item of an edit carries the post twice, as `before` and `after`, so the API caps the whole serialized post at 100 KB, with the body at 20,000 characters and the title at 200, to keep every item well inside DynamoDB's 400 KB item limit and the transaction inside its 4 MB limit. A post that is too big is refused as invalid input before any write, not by DynamoDB after it.

Attachments are checked for a second reason. A post may reference at most ten attachments, and each must point at a photo uploaded through this site's own upload route. A post therefore cannot embed an image from another host, which would let that host see every member who opened the timeline, and it cannot carry an attachment shape that breaks the page that renders it.

Comments use the table's own partitions instead. A thread's comments and reactions share one partition, so a listing reads both from it with no cross-partition fetch.

### Why the API may Scan and the edge may not

The API's role includes `Scan`, and the edge's role does not ([`infrastructure/cloudformation/app-stack.yaml`](../../infrastructure/cloudformation/app-stack.yaml)). The API needs Scan for one thing: finding every member who holds a push subscription, so that a new post can reach them. Subscriptions are not indexed by a shared key, and at family scale a filtered scan that returns only partition keys is cheap. The code says so in a comment. If the table grows large, this is the trade-off to revisit.

Everything the edge does is addressed by its own keys and index keys, never a Scan. A key the edge already has, such as a hashed token, an email, a passkey credential ID or a WebAuthn challenge, names an item directly. To find what belongs to one member, the edge Queries `GSI1`: identity links under `SUB#<gramps-id>` ([`auth/src/linkstore.js`](../../auth/src/linkstore.js)) and passkeys under `PASSKEYSUB#<gramps-id>` ([`auth/src/passkeystore.js`](../../auth/src/passkeystore.js)). Its role therefore allows `GetItem`, `PutItem`, `UpdateItem`, `DeleteItem` and `Query`, and nothing else. Leaving Scan out keeps the most internet-exposed function to the access pattern it actually uses. It is not an isolation boundary, though. Both roles are granted the whole table and its index, and the separation between their data comes from key prefixes, not from IAM.

## Notifications that say little

Push notifications leave the session boundary. They appear on lock screens and stay in a phone's notification history. The design keeps what they reveal to a minimum ([`api/src/notify.js`](../../api/src/notify.js)):

- **Level 0 by default.** Every notification's title is the site's name, "Harrison Family". Each of the four types (`comment_on_my_record`, `reply_to_me`, `mention`, `new_family_post`) has a content-free level 0 message, such as "someone replied to you." A member can opt in to level 1 for each type separately, and the lock-screen preview on the notification settings page shows the same words the registry sends. Level 1 adds the actor's label, which is never an email address (see [Labels that never publish an address](#labels-that-never-publish-an-address)), and nothing more. No notification ever carries comment or post text. Decision D-08 set this default.
- **At most one notification per recipient per event.** One comment can qualify the same member several ways. They might own the record, have commented earlier and also be mentioned with `@<gramps_id>`. They receive at most one notification. A fixed priority order picks its type from the highest reason that applies: reply, then mention, then a comment on their record. If the member has turned that type off, they receive nothing for this event, even when a lower-priority type is on. The author of the comment or post is never notified about their own action.
- **A notify failure never undoes a write, or fails it.** Notifications run only after the transaction has committed, and the whole fan-out is guarded (HFY-R58): working out who to notify (the subscriber scan on publish, the thread and post lookups on a comment) as well as sending. Any failure is logged and swallowed, and the member gets the normal success response for the write that already happened. An error response there would invite a retry, and the retry would create a duplicate post or comment. If no push keys are configured, the fan-out does no reads at all.

## Photos: presigned uploads, gated reads

A post photo never passes through the Lambda ([`api/src/uploads.js`](../../api/src/uploads.js)). The composer asks the API for an upload. The API checks the session and accepts only JPEG, PNG, WebP and HEIC images up to 10 MB. It then chooses the object key itself, `photo.<ext>` in a fresh ULID folder under `uploads/posts/`, records which member the upload belongs to, and returns a presigned PUT URL that is valid for five minutes. The URL signs the content type and the size, so S3 refuses a PUT that claims to be something other than the image the API approved. The browser sends the bytes straight to the bucket's S3 endpoint, never through CloudFront, and the post then stores the photo's metadata as an attachment.

This split puts each job where it fits. The API keeps every decision: who may upload, what type, how large, and where the object lands. The uploader's file name plays no part in the key, so it can neither steer the key out of its prefix nor carry a person's name into a URL. When a post attaches the photo, the API checks that the upload is the author's own and not yet used, and reads the front of the stored file to refuse one that still says where it was taken; the browser is meant to strip that data, but the server does not trust it to. The Lambda role can write only under that prefix. Moving the bytes is left to S3, which avoids Lambda's request-size limit (smaller than the 10 MB cap) and the time and memory of streaming a photo through a function. Because the attachment is part of the post, the audit trail records which photos a post referenced, and when.

The photos come back to the browser from the site's own origin, which makes them dangerous in one way: a file served from the site's origin with a misleading type could be run as a page with the site's privileges. So uploads get their own CloudFront behavior, `/uploads/*`, whose response headers forbid MIME sniffing and put the response in a CSP sandbox that allows nothing but same-origin images (`sandbox; default-src 'none'; img-src 'self'`, HFY-R58). Even a mislabelled upload cannot run script on the site. Both response headers policies the behavior can carry send these two headers: the app stack's uploads policy while the behavior is public, and `hfy-uploads-private` once it is gated.

### Photos are members-only

A photo in a post is family content in the same way the post's text is, so it gets the rule from [Members only, reads included](#members-only-reads-included). The API cannot apply that rule itself, because it never serves the photo. The private data gate applies it at the edge instead: [`add-data-gate-behaviors.sh`](../../scripts/infra/add-data-gate-behaviors.sh) makes `/uploads/*` the seventh gated pattern (HFY-TSK-082). It does not re-create the behavior. It updates it in place, keeping its position and its origin, and adds the `hfy-edge-gate` check of the `io_id` session, `CachingDisabled` and the response headers policy `hfy-uploads-private`. That policy keeps the two security headers and adds `Cache-Control: private, no-store`. A request without a session gets the gate's 401, or a redirect to sign-in for a page navigation.

Before that change, the behavior checked no session. A photo's URL was enough to fetch it, the random part of its ULID key was the only barrier, and Cloudflare cached the image by its extension. A URL that left the family in a copied link or a forwarded message stayed readable by anyone who had it. Gated, a photo is never stored by Cloudflare or kept by browsers, at the price of a trip to S3 for every view ([cost estimate](../reference/cost-estimate.md)). [Family data privacy](family-data-privacy.md#member-photos-are-gated-too) covers the gate's side of the change.

Members see no difference. The posts islands render a photo as a plain same-origin `<img src>`, so the browser sends the `io_id` cookie with it, and no island fetches a photo from script ([`islands/tests/uploads-gate.test.mjs`](../../islands/tests/uploads-gate.test.mjs)). A script that did fetch one would have to send `credentials: "same-origin"`. Uploading is unaffected, because the presigned PUT never passes through CloudFront ([`api/test/presign.test.js`](../../api/test/presign.test.js)). That is one more reason the split above fits: the gate on reads and the presigned grant on writes never meet.

The gate checks a session, not a post. It does not know which post a photo belongs to, so any member who holds the URL can fetch the photo, whatever the post's visibility: a photo in a draft, in a withdrawn post or left behind by a deleted one. Between members, the unguessable key is still the only barrier. That is weaker than the rule that keeps a post's discussion exactly as visible as the post ([A discussion is as visible as its post](#a-discussion-is-as-visible-as-its-post)), and it is the cost of serving photos as files rather than through the API.

Gating is a change to the distribution, not a deploy. The six data patterns were gated at the 2026-10-12 cutover, and `/uploads/*` joined the gate script later the same day. The repository does not record whether production's `/uploads/*` has been through the script since ([cut over to the private data gate](../how-to/cut-over-to-the-private-data-gate.md)). A later run of [`add-uploads-behavior.sh`](../../scripts/infra/add-uploads-behavior.sh), which builds the public behavior, leaves a gated `/uploads/*` as it is, so rebuilding the behavior cannot quietly reopen the photos. Of the repository's scripts, only `add-data-gate-behaviors.sh --remove` puts it back to the public state.

### The prefix and the leftovers

The prefix itself was chosen for the bucket's other writers. Uploads once went under `media/`, the prefix the Gramps data sync mirrors with `--delete`, so a default data sync would have deleted every member photo. `uploads/` is a prefix that no writer's `--delete` reaches ([family data privacy](family-data-privacy.md#one-bucket-for-the-site-and-the-data)).

Two consequences remain. Deleting a post removes its items, its comments and its reactions, but not the photo objects it pointed to. And a composer that is abandoned after an upload leaves an object nothing references. Nothing in the repository removes unreferenced photos. A leftover photo stays at its URL, readable by any member who holds that URL while `/uploads/*` is gated, and by anyone who holds it while it is not.

## Why the same contract tests both sides

The islands and the API are written separately, but they have to agree on the wire shape, the error codes and the permission rules. The kit packages define that agreement as contract suites: the content suite (CS-01 to CS-19) and the comments suite (CC-01 to CC-17). For the agreement between the two sides, harrisonfamily runs the kit's suites rather than writing a separate test for each side. The API also has its own tests for behavior the suites do not cover, in [`api/test/api.test.js`](../../api/test/api.test.js).

- [`api/test/contracts.test.js`](../../api/test/contracts.test.js) runs both suites against the real API stores over an in-memory DynamoDB fake. These are the same `createContentSource` and `createCommentSource` the handler calls, so the transactions, audit items and Q-4 checks are what get tested.
- [`islands/tests/content-contract.test.mjs`](../../islands/tests/content-contract.test.mjs) runs the content suite through the islands' posts adapter, with a mocked `fetch` that drives the real API handler. One test covers the adapter, the HTTP layer, session checks and server rules together. Cases that do not apply are reported as not applicable, never counted as passes.
- [`islands/tests/contract.test.mjs`](../../islands/tests/contract.test.mjs) runs the comments suite through the islands' comment adapter. Its mocked API is the kit's in-memory store behind the same routes and error body, not the real handler. The comments side is therefore held to agreement by both ends passing the same suite, not by one test that spans them.

Each side runs the suite version it pins, and the two pins are separate and can differ: [`api/test/kit-pins.test.js`](../../api/test/kit-pins.test.js) checks only that each is exact. A rule that changes in the kit therefore reaches each side only when that side upgrades, and then fails there if that side has not caught up. Drift between the halves shows up at upgrade time, not before. [Run the tests](../how-to/run-the-tests.md) lists the commands.
