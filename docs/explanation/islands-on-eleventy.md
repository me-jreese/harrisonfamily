# Why React islands on a generated Eleventy site

The harrisonfamily front end is two things layered on each other. Underneath is a static site that Eleventy renders from a private Gramps export. On top of it sit small React applications, called islands, that each take over one part of a page when its feature flag is on. In the repository, `11ty/` holds the rendered site, not the templates that produce it. The build that bundles the islands has also taken on a second job: it writes the design system's theme layer, fonts, copy and asset versions into those rendered pages.

This page explains why each of those choices was made and what the split costs. The mechanics (which flag loads which bundle, which file mounts where) are in the [front-end reference](../reference/front-end.md), and the exact build outputs are in the [theme and asset build reference](../reference/theme-and-asset-build.md).

## The starting point: a static site from a private export

Gramps is the source of truth for family records. An ETL step turns its export into per-person JSON and media files, and Eleventy renders ten pages (home, about, contact, search, person, the family route (a redirect to the member's own page), sign-in, signed-out, and the privacy and terms pages) into plain HTML, CSS and JavaScript. The pages committed to the repository carry no per-person records. Person data and media sit in the site bucket under their own prefixes, and the person and search scripts, and the islands that read the same files, fetch them from the CDN at runtime. What those requests carry depends on `authV2`. With it on, they send the `io_id` session cookie that the auth edge sets, which is what the private data gate checks on the paths it guards. With it off, they send the legacy `X-HFY-Session` header once someone has signed in, as they did before E5, and the gate does not accept that header.

A static site suits this project for four reasons:

- **Cost.** Serving files from S3 through CloudFront needs no server running while nobody visits. The main metered compute sits behind `/auth`, `/api` and `/mcp`, and the API Lambda serves both `/api` and `/mcp`. The rest is the retired legacy sign-in pieces, which stay in AWS and Google Cloud until io retires them but which no push deploys any more (the `hfy-check-allowed` Lambda, and the allowlist Cloud Function that its own manual workflow can deploy), the `HFYAppendIndex` CloudFront Function on the default behavior, and two small Lambda@Edge functions: the data gate, which runs on every request to a gated path, and the function that restores the `WWW-Authenticate` header on `/mcp` 401 responses. The [cost estimate](../reference/cost-estimate.md) prices the app backend separately from the static-site baseline.
- **Privacy.** The build output is a tree of files that can be read before it ships. That tree is not private by construction, though. Every Eleventy build, the production build included, copies the person, family, event, note, place and media data into `_site/`. The boundary is the exclude list applied when `_site/` is copied into `11ty/` and when `11ty/` is synced to the bucket. Its private-data paths appear in four places. The refresh command in `11ty/README.md` and the one in the refresh how-to apply them when `_site/` is copied. The pre-commit check, `scripts/check-deployment-sync.sh`, uses them only to compare `_site/` with `11ty/`, and copies nothing. The site deploy target in `ci.manifest.yaml` applies them when `11ty/` is synced to the bucket. `scripts/infra/test/run.sh` compares only the README command with the check, and fails when they differ. Nothing compares either of them with the how-to's command or the deploy's list. Before that test existed nothing compared any of them, and the refresh command that `11ty/README.md` carried before E5 omitted `place/`. [Refresh the Eleventy output](../how-to/refresh-the-eleventy-output.md) gives a command with the full list, and [family data privacy](family-data-privacy.md) explains the wider model.
- **A small attack surface.** No server renders the pages and no database stands behind them. The only dynamic origins are the auth edge and the API, both behind the CDN. The data gate runs at the CDN itself and checks the session cookie before a private data path reaches the bucket (see [edge and origin design](edge-and-origin-design.md)).
- **Pages that work without a framework.** The public pages are complete HTML. The member pages use plain scripts. Nothing in the base site depends on React, which is what allows React to be added a piece at a time.

## Why islands instead of an SPA rewrite

Release 1 of E5 added a new app shell, a new search, notes and comments on person pages, posts, and notifications. Building these as a single-page application would have meant replacing pages that already worked, moving routing into the client, and shipping everything at once. Islands do the reverse. They enhance pages that already exist, one surface at a time.

Three properties make that safe:

- **Each island owns one surface.** The shell owns the navigation frame on every page. The search island owns `/search/`, and the person island owns notes and comments on the person page. The posts islands own the composer on a member's own person page, the homepage timeline and `/posts/`, the notifications island owns `/me/notifications/`, and the settings island owns `/me/` (`navMe`). An island either creates its own host element beside the content it enhances, or mounts into a `[data-island="<name>"]` slot that the static page already contains ([`islands/src/lib/mount.jsx`](../../islands/src/lib/mount.jsx)).
- **Failures fall back to the page without the island.** The loader in [`11ty/js/feature-flags.js`](../../11ty/js/feature-flags.js) injects an island's bundle only when its flag resolves on. If the shell bundle fails to load, the loader removes the shell class and the old navbar returns. The Lunr search page is gone (HFY-TSK-317), so if the search bundle fails, `/search/` stays empty: the search island is the only search. `/posts/`, `/me/` and `/me/notifications/` are new pages with no legacy version. Their only fallback is static placeholder text, which stays on screen if the bundle fails or the flag is off. Islands that act only after they load (person notes and comments, the timeline, the own-page composer) need no fallback, because a failed load leaves the page as it was. Any failed island also ends a tester's preview override, so a broken preview does not follow them from page to page.
- **Turning a flag off restores the page it replaced.** A flag that resolves off fetches no island bundle, and with `authV2` off the new sign-in script exits without changing the page. With every flag off, the E5 surfaces are deployed but inert: the three new pages show their placeholder text, the service worker, manifest and offline page sit in the bucket with nothing registering or linking them, and each page fetches the flags file only to learn that its flags are off. Every surface shipped in that state first (HFY-R8), and turning it on was a separate, approved change. For the production cutover on 2026-10-12, HFY-TSK-069 set all six flags to `true` in [`11ty/_data/flags.json`](../../11ty/_data/flags.json). To see the build-time values production serves now, read `https://<site>/_data/flags.json`.

The flags do not cover the design system. The theme layer, the self-hosted fonts and the family-voice copy are written into every page by the islands build ([below](#what-the-islands-build-writes)), so every visitor gets them whatever the flags say, and only a revert takes them out again.

This is what makes the [release model](release-model.md) work. Each flag can be turned on independently, by build-time file or for one browser tab with an override ([toggle a feature flag](../how-to/toggle-a-feature-flag.md)). Turning a flag off is the rollback, with one exception: `authV2`. The private data gate accepts only the `io_id` cookie, and only the page scripts that run with `authV2` on refresh it, so with `authV2` off and the gate attached, the person and search scripts cannot read family data once the hour is up. The 2026-10-12 cutover attached the gate (HFY-R67), so turning `authV2` off cannot be the rollback while the gate stays attached. A rollback reverses the cutover's order: the gate comes off first, and the flag only after that. Anything else that puts `authV2` back to `false` carries the same hazard, including a revert of the flip and the pipeline's automatic rollback to a site artifact from before the flip, which restores that artifact's `flags.json`. Removing the gate no longer gives that client its data back on its own, either. Since the gate hardening (HFY-TSK-082), the repository's `HFYAppendIndex`, the CloudFront Function on the default behavior, denies the private data paths by default ([`scripts/cloudfront/append-index.js`](../../scripts/cloudfront/append-index.js)). Once the six gated data behaviors are gone, requests for those paths fall through to it and get `404` from every client, so person pages, search and family media stay broken unless the function is rolled back as well. The three states are therefore `401` while the gate is attached, `404` without it under the default-deny function, and `200` only under the function's older code. [Cut over to the private data gate](../how-to/cut-over-to-the-private-data-gate.md#roll-back) has the checks and the steps. The cutover ran in the matching order: `authV2` was flipped and the site deployed first, and the gate was attached only after that was confirmed live ([cut over to the private data gate](../how-to/cut-over-to-the-private-data-gate.md)). The flags have one coupling: `searchV2` implies `shellV2`, because the search launcher lives in the shell.

## Why the islands use shared @io-kit packages

The islands are thin. Most of what they render comes from io-wide packages: `@io-kit/shell`, `search`, `search-ui`, `md`, `comments`, `content`, `notify` and `tokens`, all pinned to exact versions in [`islands/package.json`](../../islands/package.json). These components are shared across io's projects rather than written for this site.

Where a package needs data from the site, it can define a contract for it and ship a suite that tests an implementation against that contract. Two packages are used that way here: `@io-kit/comments`, with its comment source, and `@io-kit/content`, with its content source. The harrisonfamily side writes an adapter against its own `/api` for each and proves it by running the kit's suite in [`islands/tests/`](../../islands/tests/). The comments suite runs against a mocked `/api` backed by the kit's in-memory store. The content suite drives the real `api/` handler. That keeps the site-specific code to the part that is specific to this site.

The shell is `KitShell` in its bare frame. The site uses the kit's navigation registry, scroll hooks, sheet and PWA-install hook, and lays out its own frame with them, following the design system's shell spec: a five-item bottom bar below 688 px (four items while `navMe` takes "family" out of it), a top bar with the links and an inline search field from 688 px, and no sidebar at any width. It supplies its own install card on top of the install hook ([`islands/src/islands/shell.jsx`](../../islands/src/islands/shell.jsx)).

The look comes from the kit too, but not at run time. `@io-kit/tokens` publishes a harrisonfamily theme, and the islands build compiles it, together with the kit's Bootstrap and kit bridges and the site's own partials, into one static stylesheet that every page links. The legacy pages and the islands therefore read the same `--io-*` tokens. Where the kit falls short, the site bridges the gap until the kit closes it:

- `@io-kit/shell`, `content` and `notify` still read the short variable names of the Enceladus theme, so one theme partial maps those names onto harrisonfamily tokens (DVP-TSK-A73). The shell also still names the Enceladus stack, but no harrisonfamily style keys on that name; its colours come from the static layer.
- `@io-kit/search-ui` has no harrisonfamily search theme yet. Version 1.0.10 put its defaults at zero specificity (DVP-TSK-A72), so the site's values win without the shell-only override it once needed. The Cloudscape half of the search theme is generated at build time from [`islands/src/lib/cloudscape-theme.js`](../../islands/src/lib/cloudscape-theme.js), so the island ships a static stylesheet instead of Cloudscape's theming runtime.

The brand fonts come from packages as well, but not from a font service: the build copies them from exact-pinned `@fontsource` packages and serves them from the site's own origin. [The design system theme layer](design-system-theme-layer.md) explains these choices.

The cost is access. The packages are published to a private AWS CodeArtifact registry, which [`islands/.npmrc`](../../islands/.npmrc) points the `@io-kit` scope at. Every install needs a short-lived registry token, which CI does not have. That is why [`scripts/ci/build-islands.sh`](../../scripts/ci/build-islands.sh) refuses to run without one, and why the build's outputs are committed ([below](#what-the-islands-build-writes)). The font packages are public, but they arrive through the same install, so building the theme needs the token too.

## Why 11ty/ holds output, not source

The Eleventy source (templates, data files, public scripts and styles) lives in the private Dropbox project workspace, `<eleventy-source>`, next to the private data it reads. Its data files load person and media data from a sibling directory at build time. Its config also copies that data into `_site/` on every build, not only for local preview, so the build output always contains it and only the exclude lists keep it out of `11ty/` and the bucket. Keeping the source there keeps the private inputs, and the code that reads them, out of Git.

The repository carries the deployable artifact instead: the rendered HTML, CSS and JavaScript that are safe to publish, and the islands build's output, which the deploy pipeline syncs to the bucket as committed. The pipeline builds nothing and patches nothing, so Git records what shipped, and a reviewer never has to reason about what a template might render.

## The consequence: two sources of truth

E5 was built in the repository, against the artifact. Its front-end work was written directly into `11ty/`: the build-time flags, a new sign-in script and its include on each rendered page, edits to existing scripts, the PWA files, and two new pages. The edited scripts carry most of the client logic:

- `js/feature-flags.js` gained the flag resolver and the island loader. It also holds the authV2 data API: `dataFetch` sends the `io_id` cookie, refreshes a lapsed edge session through `/auth/refresh`, and retries a gate 401 once before it sends the visitor to sign in (HFY-R66). It also lays the edge session over the page's default state, so My Record and Log out show for a member who signed in at the edge. The gateway session, the Google token handling and the navbar search it used to serve are gone (HFY-TSK-317). Since the design-system pass it also links the theme layer on any page that lost its link, and it carries a block of asset versions that the islands build rewrites.

- `js/person-page.js` gained the authV2 data path through `dataFetch`, and a "Sign in again" link for a session that cannot be recovered without risking a redirect loop. The design-system pass rewrote how it renders a person, but not those paths.
- `js/auth.js` (the legacy Google sign-in), `js/search-navbar.js` and `js/search-results.js` (the Lunr search) are deleted (HFY-TSK-317). `family-login/index.html` is a redirect page to `/auth/login`.

The [front-end reference](../reference/front-end.md#what-11ty-contains) lists each file. The design-system pass then added a second kind of repo-owned content: files that only the islands build produces (the theme layer, the sign-in stylesheet and the fonts), and edits that it makes to the rendered pages themselves ([below](#what-the-islands-build-writes)).

`11ty/` is the authoritative copy of this work, and `<eleventy-source>` does not reproduce it. Its templates do not emit the `auth-v2.js` include, its copies of the edited scripts lack the authV2 data path, and its layout still writes the retired Google sign-in, the Lunr search and the gateway config into every page. Its head partial already emits the two theme blocks, but with a hard-coded theme version and font file name, and it carries neither the family-voice copy nor the asset versions. For E5, `11ty/` is not output at all. The site now has two sources of truth, and some of the tools around `11ty/` still assume it has one:

- A refresh with the command that `11ty/README.md` documented before E5 rebuilds the source and runs `rsync -a --delete` from `_site/` into `11ty/`. It excludes `README.md`, `media/`, `person/`, `family/`, `event/`, `note/` and `private/`, and nothing else. Such a refresh therefore deletes every repo-owned file the source does not produce, the theme layer, the sign-in stylesheet and the fonts among them, and overwrites the edited scripts and pages with the source's versions. It also replaces `_data/flags.json` with the source's copy or deletes it, and either can turn `authV2` off without anyone deciding to. The E5 edits to `person/index.html` and `private/index.html` survive only because those directories are excluded. With the gate attached, none of this fails quietly. A visitor whose flags resolve `authV2` off sends only the legacy header, which the gate refuses, and the source's `js/person-page.js` waits for the legacy `X-HFY-Session` token, which an edge sign-in never mints, so a refresh that reverts it breaks person pages. The README's current command excludes every repo-owned path.
- Even that command cannot keep what the islands build wrote into the pages it refreshes. A refreshed page comes back without the family-voice copy and the asset versions, and with the theme blocks as the source last rendered them. So every refresh, and every run of the promotion script below, has to be followed by `cd islands && npm run build`, which puts them back, and `npm run check:islands`, which fails until it has. A page committed without that rebuild names its scripts and stylesheets by unversioned URLs again, which Cloudflare's static cache can serve stale for hours after the next deploy.
- The session-log promotion script, [`scripts/promote_workspace_assets.sh`](../../scripts/promote_workspace_assets.sh), has no exclude list. It copies a file entry with `rsync -a` and deletes nothing for it, but mirrors a directory entry with `rsync -a --delete`, which removes destination files the source lacks. A listed repo-owned file such as `js/person-page.js` is overwritten, and a listed directory such as `js/` or `css/` can delete repo-only files such as `js/auth-v2.js` or `css/hfy-theme.css`.
- The pre-commit parity check, [`scripts/check-deployment-sync.sh`](../../scripts/check-deployment-sync.sh), compares `_site/` against `11ty/` with a dry-run `rsync --delete`. It treats the repository's files as repo-owned and excludes them: the E5-only files, the islands build's files (`js/islands/`, `css/hfy-theme.css`, `css/auth-edge.css` and `fonts/`), and the repo-owned files, `js/person-page.js` and `family-login/` among them. `11ty/README.md` names the same paths in its repo-owned table and its refresh command, and [`scripts/infra/test/run.sh`](../../scripts/infra/test/run.sh) fails if the README's command and the check exclude different paths (apart from `.DS_Store`), or if the check, the command or the table drops `js/person-page.js`, `family-login/`, `css/auth-edge.css`, `css/hfy-theme.css` or `fonts/`. The check still compares the rendered pages. They differ from the source's by the `auth-v2.js` tag and by everything the islands build writes into them, so they count as drift whenever `11ty/` files are staged, until the source produces all of it.

There are two ways to get back to one source of truth, and neither is done:

1. **Mirror E5 into the source.** Port each E5 file and edit into `<eleventy-source>`: static files into `public/`, the script include and the two new pages into templates. The head partial is partly there, and the family-voice copy and the asset versions are not. `11ty/` then becomes the output of Eleventy followed by the islands build, and a refresh is safe as long as the islands build runs after it. The port has to be done and checked by hand, and the source stays outside Git, so front-end review still happens on rendered output.
2. **Move the source into the repository.** Bring the templates and public assets under Git, and keep the private data and the readers that load it outside. The source's data files and config assume sibling private directories, so separating them is real work. A CI build would also need either access to the private data or a source that no longer needs it.

Either way the islands build stays authoritative for the theme blocks, the copy and the asset versions: it rewrites them on every run, whatever the source emitted. Until one of the two is done, treat the repo-owned files in `11ty/` as hand-maintained, refresh only with a procedure that preserves them, and rebuild the islands after every refresh ([refresh the Eleventy output](../how-to/refresh-the-eleventy-output.md)).

## What the islands build writes

[`islands/build.mjs`](../../islands/build.mjs) started as the island bundler, and that is still its first job. It bundles each `islands/src/islands/*.jsx` with esbuild into `11ty/js/islands/<name>.js` and `<name>.css`, splits the shared code (React and the kit packages) into content-hashed chunks, and copies the kit's notification service-worker module alongside them.

The design-system pass (HFY-TSK-084) and the asset-versioning change (HFY-TSK-086) gave it more, because it is the only front-end build, and the only one that installs `@io-kit/tokens`, the package the theme comes from, and the brand font packages. One run now also writes the static theme layer, `css/hfy-theme.css`; the auth edge's sign-in stylesheet, `css/auth-edge.css`; the self-hosted font files in `fonts/`; the manifest's colours; two theme blocks in the head of every page; the family-voice copy on the ten Eleventy pages; and a `?v=<hash>` on every same-origin script, stylesheet and manifest reference in the pages. Outside `11ty/`, it stamps the sign-in stylesheet's version into the auth edge's manifest, [`auth/edge.manifest.json`](../../auth/edge.manifest.json). The [theme and asset build reference](../reference/theme-and-asset-build.md) lists the outputs exactly, and [change the theme or brand fonts](../how-to/change-the-theme-or-brand-fonts.md) is the procedure for changing them.

Writing into pages that Eleventy produced is a deliberate compromise, and each part has its own reason:

- **The theme link must block rendering.** `feature-flags.js` runs at the end of `<body>`, too late to hold back the first paint, so the theme has to be linked from each page's own head. [The design system theme layer](design-system-theme-layer.md) explains why.
- **The copy belongs in the Eleventy source,** which has not been ported. Until it is, the build rewrites the old copy on the ten Eleventy pages, matching only the old strings, and never touches prose that the family wrote.
- **The versions are content hashes of the build's own outputs and of the files the pages reference,** so only a step that runs last can know them.

The versions exist because of Cloudflare. It sits in front of CloudFront, caches static files (scripts, stylesheets, fonts and `sw.js`) for four hours under the URL first fetched, and never sees CloudFront's `/*` invalidations. It does not cache the HTML. Before the versions, a deploy left visitors with a mix of old and new files for hours, such as an old shell bundle under new CSS. With a `?v=` taken from the file's content, a changed file gets a URL that Cloudflare has never cached, and the HTML that names it is always fetched fresh. URLs that a script builds at run time (the island entries, the manifest, the service worker and the theme fallback) read the same hashes from a block that the build stamps into `js/feature-flags.js` and `sw.js`. Island chunks and fonts need no query, because their file names already carry a content hash. The versions do not close every gap: the pipeline syncs all of `11ty/` in one pass rather than the HTML last, and CloudFront's default cache policy ignores the query string, so CloudFront keeps the old file under a new `?v=` until the `/*` invalidation reaches it, and Cloudflare can then keep those old bytes under the new URL for up to 4 h ([edge and origin design](edge-and-origin-design.md#static-files-and-versioned-urls-hfy-tsk-086)). And the pipeline swaps the Google client ID into `js/auth.js` and the pages only after the hashes were taken from the committed placeholder, so a new client ID ships under an unchanged `?v=` ([rotate the Google client](../how-to/rotate-the-google-client.md#verify)). [Edge and origin design](edge-and-origin-design.md#caching-posture) explains the caching this fits into.

All of it is committed (HFY-R58). Building needs the private package registry, which CI cannot reach, and the deploy only syncs what is in `11ty/`. An output that is not committed would never ship, and one uploaded by hand would be deleted by the next deploy. [The release model](release-model.md#why-island-bundles-are-committed-output) explains the trade-off. The build writes only files that changed, and keeps `js/islands/` and `fonts/` to exactly its outputs. `npm run check:islands` rebuilds in memory and fails on any output that is missing, stale or extra, so it catches a page that lost its theme blocks, copy or versions as well as a stale bundle. One output needs more than a commit: the auth edge reads its manifest from its own deployed code, so a new sign-in stylesheet version reaches visitors only once `hfy-auth-edge` is redeployed ([deploy the app stack](../how-to/deploy-the-app-stack.md)).

The build's own files (`js/islands/`, the theme layer, the sign-in stylesheet and the fonts) have exactly one source, so they are never refreshed from `<eleventy-source>` or mirrored into it. The pages have two writers, Eleventy first and the islands build second, which is why every refresh ends with a build.

## The PWA rides on the shell island

Installability and offline support are capabilities of the shell island, not of the site. With `shellV2` on, the shell island registers the service worker and offers to install the site, and the loader links the manifest only once the shell has actually loaded, so a failed shell never advertises an installable app. Nothing else registers the worker. The theme colour is no longer part of this: it is a static meta tag in every page's head, set to the theme's surface colour, and the build writes the same colour into the manifest.

The worker is versioned like everything else. The shell registers `/sw.js?v=<hash of sw.js>`, and the worker names its cache after that hash. `sw.js` carries the hashes of the files it precaches, so any change to the worker or to those files gives a new registration URL, which Cloudflare has never cached, and a new cache. The new worker takes over at once and deletes every other cache. It precaches the theme layer, the shell bundle and its stylesheet, and the manifest at the versioned URLs the pages request, and the offline page and an icon at their plain paths. It answers failed page navigations with `offline.html`, which uses the precached theme and loads no scripts. It leaves `/auth` and `/api` alone, and imports the kit's notification module for push and notification-click deep links ([`11ty/sw.js`](../../11ty/sw.js)). It fetches the stable names, the island entry modules among them, network first, so that after a deploy an entry module always matches the hashed chunks on the server, and keeps one cached copy of each for offline use. It keeps chunks and fonts cache first, because a hashed name never changes content.

So installability and the offline page follow `shellV2`, and so does push delivery, which also needs a subscription made on `/me/notifications/` under `notifyV2` and a VAPID key pair on the API ([turn on push notifications](../how-to/turn-on-push-notifications.md)). With `shellV2` off, new visitors get no manifest and no worker. Turning the flag off does not unregister a worker that a browser has already installed, though. That worker keeps serving the offline page for failed navigations until it is replaced or removed, and since the 2026-10-12 flip turned `shellV2` on for every visitor, any browser that has visited since may hold one.
