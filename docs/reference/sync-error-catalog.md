# Sync error catalog and its tests

Every way the desktop sync and the cloud store are known to fail has a row in the error catalog, and every row has at least one named test that triggers it (HFY-TSK-150, review SI-21). This page is the map from row to test. The table is generated from [`scripts/ci/sync-error-catalog.json`](../../scripts/ci/sync-error-catalog.json) by [`scripts/ci/check-sync-catalog.mjs`](../../scripts/ci/check-sync-catalog.mjs), and CI fails when the map, the tests or this page disagree.

Basis: the error-handling catalog of the sync design (section 17: desktop rows D01 to D43, cloud rows S01 to S18) as amended by BRD2 section 11.1 (rows D44 to D52 and S19 to S22 added, D07 and D19 repaired), in [`docs/design/hfy-pln-002/`](../design/hfy-pln-002/). The catalog has 52 desktop rows (D01 to D52) and 22 cloud rows (S01 to S22). For what to do when a row fires, see [Sync Gramps with the website](../how-to/sync-gramps-with-the-website.md) and [Operate the sync store](../how-to/operate-the-sync-store.md).

## What the check enforces

`node scripts/ci/check-sync-catalog.mjs` reads files and nothing else (no install, no network, no CodeArtifact, HFY-R62). It is the last entry of the `tests` key of `ci.manifest.yaml`, so every pull request runs it, and it exits 1 on any of these:

| Problem | Meaning |
| --- | --- |
| `gap` | A row from D01 to D52 or S01 to S22 has no entry, no failure text or no test. |
| `unknown row ID` | The map holds an ID that is not in the catalog (D53, S23, a typo). |
| `no such test in the file` | A mapped test was renamed, deleted or skipped, or is not one the runner finds. The name is the method (`def test_x`) in a Python file, inside a class that has a base class and is not under an unconditional `@unittest.skip` or `@expectedFailure`; the exact title of an `it("...")` or `test("...")` call in a JavaScript file (not `.skip` or `.todo`); or the label of a `CURRENT="..."` line in the infra test runner. |
| `wire code` | One of the refusals of the write path listed under [The wire codes](#the-wire-codes) has no entry, no failure text or no test, or the map holds a wire code the checker does not know. |
| `the file is not in a test suite` | The file is outside the five suite folders below. |
| drift | This page's table is not what the map renders. Run `node scripts/ci/check-sync-catalog.mjs --write-doc` and commit both files. |

The check proves the map is complete and current and that each mapped test is declared and not skipped. It does not run the tests, and it cannot tell an empty test from one that asserts something; the suites run them, and a mapped test that fails fails its own suite.

## Where the tests run

| Suite | Command | Runs |
| --- | --- | --- |
| Gramps unit | `python3 -m unittest discover gramps/tests/unit` | CI and any worker. A fake Gramps tree, a fake website over the synthetic fixture, an in-memory table for the renderer. Standard library only. |
| api | `cd api && npm test` | A worker with `CODEARTIFACT_AUTH_TOKEN`. The real route handlers over an in-memory DynamoDB. |
| infra | `bash scripts/infra/test/run.sh` | CI and any worker. Stack templates and the bucket-policy script against a stub `aws`. |
| Gramps lane | `gramps/tests/gramps/run.sh` | io's Mac with Gramps 6.0.6: the real addon in the real Gramps, on copies of the fixture tree. |
| Gramps e2e | `gramps/tests/e2e/run.sh` | io's Mac with Gramps 6.0.6: the installed addon, the real Gramps command line and the sync dev server. |

Rows that fire only inside Gramps (an edit window, a lock, the one-transaction apply) have a test in the Gramps lane as well as the unit lane. Rows that cross the wire (a lost response, a 409, a revoked sign-in) have an e2e test as well, against the dev server and never the live store.

## The wire codes

The write path of the sync store (`api/src/sync`: the validator and `applyBatch`, HFY-TSK-245) refuses a bad batch with a status, a `code` and, for a content refusal, `details.violations` (a `rule`, a `pointer` and the class and handle, never a value). Each has a named test in the api suite. The list of codes is `WIRE_KEYS` in the checker: a code on it with no test fails the check, and a code in the map that is not on it fails too. The checker does not read the write path, so a new code is added to `WIRE_KEYS`, the map and its test together. A key is `<status> <code>`, with the rule after it where a code carries rules; `schema.*` and `media.rect.*` stand for every rule of the family.

## Behaviour added with the map

Six rows had no test of their own when the map was made: D19, D34, D39, D40, S13 and S15. D39 and S15 had no behaviour behind them either, and S13 rendered the right file but raised no alarm. The new tests live in [`test_sync_catalog_rows.py`](../../gramps/tests/unit/test_sync_catalog_rows.py) and [`test_render_lambda_catalog_rows.py`](../../gramps/tests/unit/test_render_lambda_catalog_rows.py).

- **D19.** The pull plan already froze an object whose change would leave a dangling reference or a one-sided family link, and reported it as an `integrity` conflict that names the class and the Gramps ID. The apply-time check inside the transaction is only the backstop. The tests pin that a dangling reference from the website, and an incoming delete of a note a person still uses, end as `partial` (exit 20) with that conflict on every run, never as a `refused` (exit 65) abort that would repeat, and that the conflict ends when the website drops the reference.
- **D34.** A media folder that cannot be written defers that media object and what refers to it; the rest of the pull applies, and the next run after the folder is fixed finishes the download.
- **D39.** A snapshot line of a class the addon does not know is parked: it counts toward the header's `count`, is listed under `deferred` in the preview (`a kind of object this addon does not know: update the addon`), and the rest of the pull applies. The earlier behaviour refused the whole snapshot as invalid. An object whose top-level keys include one the addon does not know is parked the same way, with the key names in the preview, and so is a new object that refers to a parked new object. The push sends nothing for such an object (`cloud_unknown_field`), because a push built from the local copy would drop the field from the website. The known keys are in [`knownfields.py`](../../gramps/hfygramps/addon/knownfields.py), and a unit test compares them with the Gramps schema export, so a schema change fails until the table follows. Only the top level of an object is checked; a key nested inside a list element is not. The push never meets a class it does not know: the push-time snapshot reader drops such a line (`continue` in `read_snapshot_bytes`), so nothing of that class reaches the merge, and every local object has a known class. The delta pull (the change feed, HFY-TSK-277) gives the same answer: a replica holds heads only and would drop a parked line from the body, the count and the plan, so a cached state that holds one is not used as a base (`unknown_class` in the run log), and a feed op of an unknown class is `bad_op`; both fall back to the full snapshot, which parks the object, so the preview, the exit code and the 7th-sync verification are the same whichever route the run takes.
- **D40.** An object over the website's size limit (204,800 bytes) is held with the rule `object_too_large` and none of its text is sent; the rest of the batch goes, and trimming the object sends it on the next run.
- **S13.** Two live heads with one Gramps ID render the first by (Gramps ID, handle) order, and the renderer raises the `HeadMismatch` alarm on every pass that reads the store while the condition holds.
- **S15.** A log entry whose object does not hash to its own `hash` is skipped: the object keeps the version before that entry, the pass and the cursor go on, and the renderer raises the `HeadMismatch` alarm until a later good entry (or `rebuild-heads`) replaces it. Only counts reach the metric and the log. Only the renderer reads the log, so only it protects itself this way: the snapshot a desktop pulls is built from the head rows (`api/src/sync/pull.js`) with no per-entry hash check, and `api/src/sync/refold.js` reports `hash_mismatch` when the heads are rebuilt from the log.
